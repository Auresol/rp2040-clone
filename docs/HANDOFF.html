What This Is

A microcontroller is a chip that contains three things in one package: a CPU (the thing that runs instructions), memory (where those instructions and data live), and peripherals (circuits that talk to the outside world — toggling a pin, sending a pulse, reading a button). The RP2040 is one such chip, made by Raspberry Pi.

This project builds a microcontroller from scratch that works the same way. Instead of designing physical silicon directly, everything is described in RTL (Register Transfer Level) — a hardware description language called SystemVerilog. That description is then either simulated on a PC (for testing), mapped onto an FPGA (for running on real hardware), or eventually sent to a chip foundry to be fabricated in silicon.

The current target is the AMD Kria KR260, a development board that contains an FPGA. The FPGA is loaded with a bitstream (see Background Concepts) that makes it behave like the microcontroller. The RPi 40-pin header on the KR260 is where the GPIO pins come out.

The CPU inside this microcontroller is Hazard3, an open-source core that implements the RISC-V instruction set. The rest of the SoC (System on Chip) connects it to 64 KB of memory, a GPIO peripheral, and a PIO subsystem copied from the RP2040.

Formal Verification

Formal verification proves that the RTL is correct for all possible inputs and sequences of events, not just the specific scenarios covered by simulation tests. Instead of running a firmware binary and checking the output, you write properties — statements that must always be true — and a solver mathematically checks whether any sequence of inputs can violate them.

The tool used here is SymbiYosys (open source), which drives solvers like Yices and Z3 on top of Yosys. Properties are written in SystemVerilog assertions (assert, assume, cover).

Primary target — DMA controller

DMA is a bus master that operates concurrently with the CPU. The most dangerous class of bugs in concurrent bus masters are not caught by simulation because they require a specific interleaving of CPU and DMA activity that tests rarely exercise. Formal verification covers all interleavings automatically. Key properties to prove:

  • The DMA never issues a transaction to an address outside the range configured by the CPU.
  • The DMA never issues a write when configured for a read-only transfer, and vice versa.
  • Once a transfer is started, the DMA always completes it — it cannot deadlock waiting for HREADY.
  • The DMA relinquishes the bus between transfers so the CPU is never starved indefinitely.
  • The transfer count register reaches exactly zero when the transfer completes — no off-by-one.
Secondary target — AHB arbiter

The arbiter on main has a known bug (two-cycle grant hold — see Known Issues). The fix must be formally verified before dual-core is restored. Key properties: the arbiter never grants both masters simultaneously; a master that wins arbitration always gets a complete, uninterrupted transaction; a waiting master is never starved forever.

Where to start

Read the AHB-Lite and bus sections in Background Concepts first. Then read rtl/soc/fabric/ahb_arbiter.sv and the Known Issues section. The SymbiYosys documentation has a walkthrough for writing AHB protocol properties — start there, apply it to the arbiter, then move to DMA once that is designed.

Developer Tooling — Pin Assignment IDE & Debug Interface

The RP2040 ecosystem has strong tooling: RP2040 datasheet, Pico SDK, and graphical tools that make it easy to assign PIO programs to pins, configure clocks, and debug firmware. This SoC needs the same.

Part 1 — Pin assignment tool

A graphical tool modelled on STM32CubeMX. The user sees the RPi 40-pin header diagram. Each pin can be assigned to a function: plain GPIO (driven by the GPIO peripheral), PIO state machine output, PIO state machine input, side-set, etc. The tool knows which functions are valid on which pins (derived from fpga_top_kr260.sv and the mux logic). When the user finalises the assignment, the tool generates:

  • An updated fw/soc.h with the correct PIO_SMx_PINCTRL register values pre-filled.
  • A pinout.svg diagram of the assignment for documentation.
  • Optionally, a skeleton firmware file with the pin initialisation sequence.
Part 2 — Debug interface

Currently there is no way to inspect the SoC's internal state while it is running on the KR260. Two approaches, in increasing complexity:

  • MMIO debug peripheral (simpler) — a new AHB slave at a fixed address that the Zynq PS can read from Linux. It exposes read-only windows into the CPU's program counter, register file snapshot (sampled each N cycles), and the PIO state machine states. The PS reads these over the AXI-to-AHB bridge (once that bridge exists) and a small Python script on the board prints the state — similar to a very simple logic analyser.
  • JTAG/SWD + GDB stub (harder) — implement a RISC-V debug module (RISC-V debug specification 0.13) in RTL, exposing JTAG pins on the RPi header. OpenOCD connects to the JTAG port and provides a GDB remote target. This lets you set breakpoints, single-step, and inspect memory from GDB. Hazard3 has a debug module port that is currently unconnected — rtl/core/hazard3/ contains the relevant interface files.
Where to start

Read Background Concepts (memory-mapped I/O, PIO, AHB-Lite) and fpga_top_kr260.sv to understand the current pin mux. For the pin tool, the data model is straightforward: a mapping from pin number to function enum, constrained by what the mux supports. For debug, start with the MMIO peripheral option — it can be built and tested before the AXI bridge exists by reading from the PS side via devmem2.

Security — Crypto Accelerator & Secure Boot

Two separate but related pieces of work. Together they make the chip viable for applications where the firmware must be trusted and data must be protected.

Part 1 — Crypto accelerator peripheral

A new AHB-Lite slave peripheral that offloads cryptographic operations from the CPU. Performing AES or SHA-256 in software on an RV32IMC core is slow and blocks the CPU for the entire duration of the operation. A hardware accelerator completes the same operation in a fixed, short number of clock cycles and raises an interrupt when done, freeing the CPU.

Suggested initial scope:

  • AES-128 / AES-256 — block cipher, ECB and CTR modes minimum. The AES round function is highly parallelisable in hardware — a fully unrolled AES-128 encryption can complete in 10 clock cycles (one per round).
  • SHA-256 — cryptographic hash function. Used for integrity checks, signatures, and key derivation.
  • TRNG (True Random Number Generator) — samples thermal noise from ring oscillators to produce unpredictable bits. Required for key generation. sky130 ring oscillators can be used as the entropy source.

The peripheral fits into the address map at 0x4001_0000 (currently unassigned). The CPU writes plaintext and key into data registers, sets a control register to start the operation, and polls a status register (or waits for an interrupt) until the result is ready.

Part 2 — Secure boot

Secure boot ensures the chip only executes firmware that has been signed with a trusted key. Without it, anyone who can load a bitstream can run arbitrary code. For a tapeout chip this is essential.

The flow:

  • A small ROM bootloader is baked into the chip at fabrication time (a separate read-only memory region, not the SRAM). It cannot be modified after tapeout.
  • On reset, the CPU executes the ROM bootloader. It reads the firmware from SRAM (or an external flash), computes a SHA-256 hash, and verifies an Ed25519 or ECDSA signature against a public key stored in OTP (One-Time Programmable) fuses — small cells that are programmed once after fabrication and cannot be changed.
  • If the signature is valid, the bootloader jumps to the firmware. If not, it halts.

The crypto accelerator (Part 1) is used by the bootloader to perform the hash and signature check quickly.

Where to start

Read Background Concepts (AHB-Lite, memory-mapped I/O) and rtl/soc/peripheral/gpio.sv as a reference for how a simple AHB peripheral is structured — the crypto accelerator follows the same pattern. Start with AES-128 in ECB mode only: write the RTL for one AES round, verify it in simulation against known test vectors from the NIST AES standard, then pipeline the 10 rounds. SHA-256 and the bootloader come after.

Background Concepts

This section explains the hardware ideas that appear throughout the rest of this document. If you have designed hardware before, skip it.

What a CPU core is — and what RV32IMC means

A CPU core is a circuit that, over and over, does three things: fetch an instruction from memory, decode what it means, and execute it. Hazard3 is a 3-stage pipeline: Fetch, Decode, and Execute each run in parallel on different instructions. Every clock cycle, the pipeline advances — one instruction is fetched, a different one is decoded, and a third is executed simultaneously.

RISC-V is an open instruction set standard — it defines what instructions a CPU understands and how they are encoded in binary. No company owns it. Anyone can build a CPU that implements it.

The letters after RV32 describe which parts of the standard are implemented:

  • RV — RISC-V
  • 32 — registers and data are 32 bits wide
  • I — base integer instructions: add, subtract, load, store, branch, jump
  • M — multiply and divide instructions
  • C — compressed instructions: common instructions encoded in 16 bits instead of 32, saving code size

Hazard3 also implements Zicsr — the control and status register extension, which gives access to timer, interrupt, and exception registers.

What a bus is

Inside this SoC there are several independent pieces of hardware: the CPU, SRAM, GPIO, and PIO. They all need to exchange data. A bus is the set of shared wires and the rules (protocol) for using them — which signal means what, who is allowed to drive the wires and when, and how a receiver signals that it is ready.

Without a bus protocol, connecting multiple senders and receivers to the same wires would cause bus contention: two things driving the same wire at the same time, one pulling it high, one pulling it low — the result is undefined and can damage real hardware.

The protocol enforces that only one sender drives the wires at a time. The arbiter is the circuit that decides which sender gets access each cycle when more than one is waiting.

What AHB-Lite is

AHB-Lite (Advanced High-performance Bus, Lite variant) is the specific bus protocol used in this design. It was defined by ARM and is the same protocol Hazard3 exposes natively on its CPU ports.

A transaction on AHB-Lite happens in two consecutive clock cycles:

  • Address phase — the master (CPU) drives: HADDR (the target address), HWRITE (1 = write, 0 = read), HSIZE (byte / halfword / word), HTRANS (indicates a valid transaction).
  • Data phase — one cycle later: if writing, the master drives HWDATA; if reading, the slave drives HRDATA back.

The slave asserts HREADY low to stall the bus if it needs more time. The master must hold its signals stable until HREADY goes high.

Hazard3 has two separate AHB-Lite ports: one for instruction fetches (I-port) and one for data loads and stores (D-port). They operate independently and in parallel. This is why the SoC has two decoders — one for each port.

A decoder looks at HADDR and routes the transaction to the right slave. If the address is in 0x0000_xxxx, the decoder points to SRAM. If it is 0x4000_xxxx, it points to GPIO. And so on.

What memory-mapped I/O is

The CPU has one operation it knows how to do with the outside world: read or write to an address. It does not have a special "talk to GPIO" instruction or a special "talk to PIO" instruction. Everything goes through the same load/store mechanism.

Memory-mapped I/O works by placing peripherals at specific addresses in the address space. When the CPU writes to address 0x4000_0000, the decoder routes that transaction to the GPIO peripheral instead of SRAM. The GPIO peripheral sees the write and updates the state of its output pins. From the CPU's perspective, it just wrote to a memory address.

The firmware file fw/soc.h defines macros for every peripheral register address. Writing firmware is a matter of knowing which address controls which behavior.

What PIO is

PIO (Programmable I/O) is a subsystem in the RP2040 — and replicated here — that gives you small programmable state machines for controlling GPIO pins. Each state machine has its own program (up to 32 instructions), its own clock divider, TX and RX FIFOs for exchanging data with the CPU, and direct write access to GPIO pins.

The reason PIO exists: generating precise timing on a pin from the CPU requires the CPU to execute instructions in a tight loop with exact cycle counts. This blocks the CPU from doing anything else and breaks if an interrupt fires at the wrong time. PIO state machines run autonomously — once started, they produce or consume pin signals on their own clock without CPU involvement.

This SoC has two PIO blocks, each with two state machines (four total). The PIO instruction set has 9 instructions. It is documented in full in the RP2040 datasheet, Chapter 3.

What DMA is

DMA (Direct Memory Access) is a hardware block that moves data between two places — for example, from a peripheral's output FIFO into SRAM — without the CPU doing the work. Without DMA, the CPU must read each value from the peripheral and write it to memory one at a time, spending cycles that could otherwise run other code.

A DMA controller is itself a bus master: it can issue reads and writes onto the bus independently of the CPU. The CPU sets up the transfer — source address, destination address, number of items, item width — and then the DMA runs the transfer autonomously, raising an interrupt when done.

For this SoC, DMA is particularly useful for feeding the PIO TX FIFOs from SRAM without tying up the CPU in a copy loop, and for capturing PIO RX FIFO output into a memory buffer. The DMA controller is not yet implemented; it is the next major milestone. See Next Work.

Address Map

Every peripheral in the SoC is accessed by reading or writing to a specific range of addresses (see memory-mapped I/O above). The decoder in the fabric routes each CPU transaction to the right destination based on the top bits of the address.

RangePeripheral
0x0000_0000 – 0x0000_FFFFSRAM (64 KB) — instructions and data both live here
0x4000_0000 – 0x4000_FFFFGPIO — 32-bit output register at base address
0x5020_0000 – 0x5020_FFFFPIO0 — state machines 0 and 1
0x5030_0000 – 0x5030_FFFFPIO1 — state machines 2 and 3

The PIO register layout is identical to the RP2040 datasheet (Chapter 3). All macros are in fw/soc.h. Any address not in the table above returns a bus error — the decoder has no slave to forward it to.

Architecture Decisions

ADR-1 — CPU: Hazard3 over Ibex
Decision

Use Hazard3 as the CPU core.

Rationale

When choosing a CPU core, the main candidates for a RISC-V RV32IMC design are Ibex (developed by lowRISC) and Hazard3 (developed by Luke Wren at Raspberry Pi).

Ibex is designed to replace an ARM Cortex-M3 — a mid-range embedded core. It has a 2-stage or 3-stage pipeline with branch prediction, a larger footprint, and more configurability than needed here.

Hazard3 is designed to replace an ARM Cortex-M0+ — the smallest and lowest-power ARM core. The RP2040 uses a Cortex-M0+; the RP2350 uses Hazard3 directly. This makes Hazard3 the most direct architectural peer to what we are cloning. It is also significantly smaller: Ibex typically costs ~30–40K LUTs on Xilinx FPGAs; Hazard3 fits in roughly half that.

Hazard3 exposes native AHB-Lite ports for both instruction and data access, which removes the need for any bridge logic between the CPU and the rest of the SoC.

ADR-2 — Bus fabric: AHB-Lite
Decision

Use AHB-Lite as the internal SoC bus.

Rationale

Because Hazard3 already speaks AHB-Lite natively, using the same protocol for the rest of the fabric means there is no translation layer between the CPU and any peripheral. A bridge adds latency (extra cycles per transaction) and extra logic. Avoiding it keeps every load/store at minimum latency.

AHB-Lite also has a well-defined, simple handshaking mechanism (HREADY) for peripherals that need more than one cycle to respond. The SRAM, GPIO, and PIO all implement this interface directly.

The "Lite" in AHB-Lite means there is no burst mode, no locked transfers, and no exclusive access — only the features needed for a simple single-master point-to-point transaction. Full AHB includes those features and is more complex to implement and verify.

ADR-3 — Single-core on working branch
Decision

The active branch (feat/single-core) removes the arbiter and wires CPU0 directly to the decoders. The second CPU core is disconnected.

Rationale

The RP2040 has two CPU cores that share a single bus to memory. When both cores want to access the bus in the same cycle, an arbiter decides which one goes first. The implementation of that arbiter on the main branch has a bug.

Rather than block all progress waiting for the arbiter fix, the arbiter was removed on this branch so that all other work — PIO, GPIO, firmware, FPGA bringup — could proceed with a known-good single-core SoC. The arbiter bug is described in detail in Known Issues.

All simulation tests and all hardware tests on this branch use only CPU0. The second core exists in the RTL but its AHB ports are left unconnected (tied to safe idle values).

ADR-4 — Firmware baked into bitstream
Decision

Firmware is loaded into SRAM at synthesis time via $readmemh and a .mem file, not over a runtime interface.

Rationale

When an FPGA powers on, BRAM contents are initially undefined — or whatever the bitstream specifies. The CPU starts executing from address 0x0000_0000 on the first clock cycle. If nothing put valid instructions there, the CPU fetches garbage and executes it.

There is no operating system, no bootloader, no SD card — nothing to load firmware at runtime. The only reliable way to get firmware into SRAM before the CPU's first instruction is to encode the firmware into the bitstream itself. Vivado supports this: the $readmemh directive in sram_bank.sv reads a hex file at synthesis time and sets the initial contents of each BRAM block. The result is baked into the bitstream.

The flow: compile firmware → scripts/bin2mem.py converts the binary to a hex file → saved as fpga/firmware.mem → Vivado reads it during synthesis → BRAM starts up pre-loaded. Loading a different firmware requires a full re-synthesize.

A future improvement: wire an AXI-to-AHB bridge from the Zynq PS to the PL SRAM, so the ARM cores in the PS can write firmware into SRAM directly at runtime, without rebuilding the bitstream.

ADR-5 — PIO GPIO mux in FPGA wrapper
Decision

fpga_top_kr260.sv implements a per-bit output mux: if PIO has claimed a pin (its output-enable bit is high), PIO drives it; otherwise the GPIO peripheral drives it.

Rationale

Both the GPIO peripheral and PIO state machines can write to the same physical RPi header pins. Without a mux, both would drive the same output wire simultaneously — contention. The mux gives PIO priority: a state machine that calls SET PINDIRS (sets its output-enable high) takes ownership of that pin. The CPU can still control any pin not claimed by PIO through normal GPIO writes.

The mux is per-bit, so PIO can own pins 0–3 while the CPU owns pins 4–7 simultaneously. This is the same model the RP2040 uses, except the RP2040 has additional IO_BANK0 ownership control registers that are not implemented here yet.

ADR-6 — Clock source: PS FCLK0, not a PL MMCM
Decision

The SoC clock comes from FCLK0, a clock output from the Zynq PS (the ARM processing system side of the chip), configured at 100 MHz in the Vivado block design.

Rationale

The KR260 is a Zynq UltraScale+ MPSoC — it contains both an ARM processor (PS) and a configurable FPGA fabric (PL) on the same die. The PS can output clocks directly into the PL.

The first attempt used a PL MMCM (a clock synthesis circuit inside the FPGA) driven by an oscillator expected on pin H4. That pin is not connected on the KR260 — it is present on a different board (KD240) that shares the same base schematic. With no signal on H4, the MMCM had no reference and produced an unstable output. This caused a USB over-current fault when the bitstream was loaded.

Switching to FCLK0 gives a known-good, PS-managed clock. The PS also holds the PL in reset (FCLK_RESET0_N) until it has finished booting, so the SoC never starts with an unstable clock.

Known Issues

Arbiter bug (main branch) — do not restore dual-core without fixing this

The arbiter in rtl/soc/fabric/ahb_arbiter.sv is supposed to grant bus access to one master per cycle. If both CPU0 and CPU1 want the bus at the same time, the arbiter should pick one, let it complete its transaction, then pick the other.

The bug: the arbiter holds the grant signal high for two cycles instead of one. Here is what that looks like: 

Cycle 1: Grant → CPU0.  CPU0 drives HADDR, HWRITE, HTRANS.  Correct.
Cycle 2: Grant still → CPU0 (bug).  But the arbiter has also started
         transitioning toward CPU1, so HSEL for CPU1's decoder goes high.
         CPU0 is still driving HWDATA for the previous transaction's data phase,
         but CPU1's decoder now thinks a new CPU1 transaction is in the address phase.
         CPU1 reads HADDR — which is actually CPU0's HWDATA — as its target address.
         CPU1 issues a load or store to a garbage address.

The symptom is that CPU1 reads corrupted values — its loads return data from the wrong address, or its stores go to the wrong location. The fix is to ensure the grant changes exactly on the cycle boundary between address phase and data phase. This requires tracking where in the two-phase transaction each master is and only switching grants at the end of a complete transaction.

Tracked on main. feat/single-core works around it by removing the arbiter entirely. Do not re-enable the second core without fixing and verifying the arbiter in simulation first.

SRAM write-first semantics — do not change sram_bank.sv write assignment style

In rtl/soc/memory/sram_bank.sv, the write to BRAM data uses a blocking assignment (=) instead of the non-blocking (<=) that is standard for registered logic. This is intentional and must not be changed.

Here is why. BRAM has two operating modes for what happens when you read and write the same address in the same cycle:

  • READ_FIRST: the read returns the old value (the value that was there before this write). The write still happens, but the output reflects the previous state.
  • WRITE_FIRST: the read returns the new value (the value being written right now). The output immediately reflects the write.

Vivado infers which mode to use based on the RTL. If the write is non-blocking (<=), Vivado sees a read-first pattern and infers READ_FIRST BRAM. If the write is blocking (=), Vivado sees write-first behavior and infers WRITE_FIRST BRAM.

This matters for the CPU because Hazard3 issues a store (sw) followed immediately by a load (lw) to the same address in back-to-back cycles. The pipeline is structured so the load's read happens while the store's write is still being committed. Under READ_FIRST, the load gets the old value — a stale read. The CPU appears to ignore its own store.

Under WRITE_FIRST, the load sees the new value immediately. This is correct. The blocking = in sram_bank.sv is what makes Vivado infer WRITE_FIRST. Leave it as-is.

PIO clkdiv width

The PIO clock divider in pio_sm.sv is 8 bits wide on FPGA, narrowed from the 16-bit width in the RP2040 specification. This was done to avoid Vivado inferring a wide counter that uses excessive LUTs.

The consequence: the maximum clock divisor is 255 instead of 65535. At 100 MHz this limits the minimum PIO step rate to ~392 kHz. For the current firmware tests this is not a problem. Restore to 16 bits before any ASIC work or before implementing firmware that needs very slow PIO clocking.

Build & Deploy

Run simulation (all tests)

Simulation uses Verilator to compile the RTL into a C++ model, then runs each firmware binary through it. The harness (sim/main.cpp) exits when the firmware writes a sentinel value to a specific address. Pass = firmware completes without timeout. 

# On remote machine (faster build):
make remote-test

Build and load a bitstream to KR260

Step 1 runs Vivado synthesis + implementation with the chosen firmware baked into the BRAM initial values. This takes ~15–25 minutes. Step 2 converts the raw Xilinx .bit file into a .bit.bin that the Linux FPGA manager can load. Step 3 copies it to the board and loads it — from this point the PL is the SoC and the firmware starts running immediately. 

# 1. Synthesise + implement; bake firmware into bitstream
make remote-fpga-kr260 FW=sim/sw/pio_blink.bin

# 2. Convert .bit → .bit.bin (bootgen, runs on the remote machine)
make remote-bitstream-kr260

# 3. Copy to board and load
scp fpga/bitstream/fpga_top.bit.bin ubuntu@<board-ip>:/lib/firmware/
ssh ubuntu@<board-ip> 'sudo fpgautil -b ~/fpga_top.bit.bin -f Full'

Firmware compilation

C firmware in fw/ is compiled with a RISC-V cross-compiler: riscv64-none-elf-gcc. The flags -march=rv32imc_zicsr -mabi=ilp32 tell the compiler to target RV32IMC with 32-bit integer calling convention. The linker script fw/link.ld places the firmware at address 0x0000_0000 — the start of SRAM, which is where the CPU fetches its first instruction. 

make sim/sw/blink.bin

The resulting .bin is a flat binary image, not an ELF. It is loaded directly at address 0 in simulation, or converted to a .mem hex file for bitstream baking.

DMA controller

No design started. A DMA (Direct Memory Access) controller moves data between peripherals and memory without CPU involvement — the CPU sets up a transfer (source address, destination address, length) and the DMA block executes it autonomously. It should attach to the AHB data fabric as a new slave (for its control registers) and also as a bus master (so it can issue its own reads and writes). Suggested control register base address: 0x5000_0000. Adding a second bus master means the arbiter must be fixed first.

Build a bitstream with fw/pio_pwm.c baked in and load it to the KR260. Expected result: a breathing LED pattern on one of the RPi header GPIO pins as the CPU varies the PIO duty cycle over time.

Arbiter fix

Diagnose the two-cycle grant hold in rtl/soc/fabric/ahb_arbiter.sv. The fix should track the AHB transaction phase (address vs data) and only switch the grant between transactions, not between cycles. Verify in simulation with a dual-core test that has both CPUs issuing overlapping loads and stores before merging to main.

AXI-to-AHB bridge (runtime firmware loading)

Connect the Zynq PS to the PL SRAM via an AXI-to-AHB bridge. This would let the ARM cores write firmware directly into SRAM from Linux (e.g. devmem2 or a small loader program), removing the need to re-synthesize for every firmware change. The PS would hold the SoC in reset while loading, then release reset to start execution.
