Introduction

This document explains the process of taking the RTL in this repository and turning it into a real silicon chip. It covers every stage in order, what each stage produces, what tools are used, and what can go wrong.

The target process is SkyWater sky130 — a 130 nm open-source process developed by SkyWater Technology and made accessible through the Efabless / Google MPW program. 130 nm means the smallest feature that can be reliably manufactured on the chip is 130 nanometres wide. It is not a bleeding-edge node, but it is open, well-documented, and free to use for tapeout.

The toolchain that automates the majority of this flow is OpenLane — an open-source RTL-to-GDS pipeline that wraps Yosys, OpenROAD, Magic, Netgen, and several other tools into a single run driven by a JSON config file. Most stages below happen inside OpenLane automatically; they are described individually so you understand what is happening and can intervene when something fails.

Flow Overview

Stage 1 — Convert SystemVerilog to Verilog

Stage 1 sv2v tool: sv2v

The RTL in this repo is written in SystemVerilog (.sv files). SystemVerilog is a superset of Verilog with convenient additions: logic types, always_ff, always_comb, packed structs, and more. Vivado (the FPGA tool) handles SystemVerilog natively.

Most open-source ASIC tools — Yosys in particular — have limited SystemVerilog support. The first step is to mechanically convert everything to plain Verilog using sv2v. 

sv2v rtl/soc/*.sv rtl/soc/**/*.sv -w separated
What can go wrong
Unpacked array ports

SystemVerilog allows input logic [7:0] data [3:0] — an array of four 8-bit values as a port. Plain Verilog does not support unpacked arrays on ports. These must be flattened to input logic [31:0] data before sv2v runs. This has already bitten this design once during OpenLane work.

automatic in always blocks

SystemVerilog tasks inside always blocks can be declared automatic, meaning local variables are re-created on each call. Verilog does not support this in synthesizable code. Remove automatic or restructure the logic.

$readmemh FPGA init must be removed

The SRAM in sram_bank.sv uses $readmemh to load firmware at synthesis time — this is an FPGA-only trick. For ASIC, memory is a separate hard macro and $readmemh must be removed from the RTL before synthesis.

Stage 2 — Replace FPGA Primitives with ASIC Equivalents

Stage 2 FPGA Primitive Replacement tool: OpenRAM + manual RTL edits

FPGA synthesis targets specific hardware blocks that are hard-wired into the FPGA fabric. None of these exist in a standard cell ASIC library. They must be replaced before synthesis can proceed.

BRAM → OpenRAM SRAM macro

On FPGA, the 64 KB SRAM uses RAMB36 blocks — dedicated memory primitives. In a sky130 ASIC there are no RAMB36 blocks. Memory is instead provided as a hard macro generated by OpenRAM — an open-source tool that generates SRAM layouts directly in the target process.

An OpenRAM macro is a pre-characterized black box: its timing (read latency, setup/hold), power consumption, and physical dimensions are all known before placement. It has a standard port interface that plugs into the existing sram_top.sv controller with minimal changes.

Steps:

  1. Determine the SRAM configuration: 32-bit wide, 16384 words deep (= 64 KB), dual-port (one for instruction fetch, one for data), 1-cycle read latency.
  2. Run OpenRAM with the sky130 PDK to generate the macro. Output: RTL stub (.v), timing model (.lib), and physical dimensions (.lef).
  3. Replace the BRAM inference logic in sram_bank.sv with an instantiation of the generated macro.
  4. Provide the .lib and .lef to OpenLane so the placer and router treat the macro correctly.

LUTRAM → register arrays or small SRAM macros

The PIO FIFOs in pio_fifo.sv use LUTRAM — distributed memory built from LUTs in the FPGA fabric. This does not exist in ASIC. Options:

  • Register array — for shallow FIFOs (≤ 64 entries): synthesize from plain flip-flops. Simple and correct, but area-inefficient at larger depths.
  • Small OpenRAM macro — for deeper FIFOs: generate a small SRAM macro (e.g. 32-bit × 32 entries) from OpenRAM and instantiate it.

The current PIO FIFOs are 4 entries deep (32-bit each). Register arrays are the right choice here — generating a macro for 4 entries is not worth the overhead.

Stage 3 — Synthesis

Stage 3 Synthesis tool: Yosys

Yosys reads the Verilog netlist from Stage 1 and maps it to the sky130 standard cell library — a collection of hundreds of pre-characterized logic gates, flip-flops, multiplexers, and buffers that SkyWater has physically designed and verified in 130 nm silicon. Every cell has a known delay, power, and area.

Synthesis runs in three phases:

  1. Elaboration — parse the Verilog and build an internal graph of logic operations.
  2. Optimization — simplify logic: remove constants, merge redundant gates, eliminate dead code.
  3. Technology mapping — replace abstract logic operations with actual cells from the sky130 library. For example: a 2-input AND becomes sky130_fd_sc_hd__and2_1; a positive-edge flip-flop becomes sky130_fd_sc_hd__dfxtp_1.

The output is a gate-level netlist — a Verilog file containing only cell instantiations and wire connections, no behavioral logic.

Key synthesis settings
  • Cell library variant: sky130 has variants — hd (high-density, smaller cells), hs (high-speed, lower delay), etc. OpenLane defaults to hd. Higher drive strength = lower delay, larger area.
  • Target clock period: set the intended frequency so Yosys can prioritize timing-critical paths. Start conservative — 50 MHz (20 ns period) for a first pass, tighten later.
  • Flattening: Yosys can collapse all module hierarchy into one flat netlist, which sometimes helps timing across module boundaries. OpenLane has a flag for this.
What can go wrong
Unmapped cells

If sv2v missed a construct or the RTL uses something Yosys does not recognize, synthesis fails with an unmapped cell error. Fix the RTL and re-run.

Combinatorial loops

Logic that feeds its own output back into its input with no register in the path. Yosys errors on this. The loop must be broken by inserting a register stage.

Unintentional latches

An if or case statement in a combinatorial block that does not cover all cases causes Yosys to infer a latch — a storage element that is not edge-triggered. Latches are problematic for ASIC timing analysis and usually indicate a bug. Fix by adding a default assignment at the top of the block or covering all cases explicitly.

Stage 4 — Floorplanning

Stage 4 Floorplanning tool: OpenROAD

The floorplan defines the physical space the chip occupies and where the major pieces go within it.

Die size

OpenLane estimates the total cell area from the synthesized netlist. The die must be large enough to hold all the cells plus room for routing channels between them. A utilization of 40–60% is typical — at 50% utilization, if the cells occupy 1 mm², the die is 2 mm². Too tight and the router cannot fit all the wires; too loose and the die is unnecessarily large and expensive.

I/O pad placement

Signals that connect to the outside world — clock, reset, GPIO, power — need I/O pad cells placed around the perimeter of the die. sky130 provides these from the sky130_fd_io library. Each pad is large — roughly 60 µm wide — and the number of pads is limited by the perimeter length. This constrains how many external signals the chip can have.

Power planning

Power must be distributed across the entire die:

  • Power ring — a wide loop of metal running around the perimeter of the die, connected to the VDD and GND supply pads.
  • Power straps — wide horizontal and vertical metal wires branching off the ring, crossing the die to deliver power to every region.
  • Cell rows — each row of standard cells has built-in VDD and GND rails that the straps connect to.

sky130 has 5 metal layers. met1 is used for cell-level connections and the power rails inside rows. met2 and met3 carry signals. met4 and met5 carry power straps and the clock trunk.

Hard macros (the SRAM from Stage 2) are placed in the floorplan step, before standard cells. Their position is usually chosen manually — placed in a corner or along an edge to avoid blocking standard cell rows.

What can go wrong
Die too small for I/O pads

If the perimeter of the chosen die size is shorter than the total width of all required I/O pads, the floorplan fails. Fix: increase die size, reduce pin count, or multiplex signals onto shared pads.

IR drop in power grid

Metal wires have resistance. If power straps are too narrow or too sparse, regions far from the supply pads see a lower effective voltage due to the resistive drop. Lower voltage = slower logic = timing failures. IR drop is checked in sign-off (Stage 8). Fix during floorplan by widening straps or adding more of them.

Stage 5 — Placement

Stage 5 Placement tool: OpenROAD

The placer positions every standard cell from the gate-level netlist inside the die, within the rows defined by the floorplan. The primary objective is to minimize total estimated wire length — cells connected to each other should be physically close so wires between them are short, reducing delay and routing pressure.

Placement runs in two phases:

  1. Global placement — roughly positions cells to minimize estimated wirelength, without requiring cells to be on legal row-aligned positions.
  2. Detailed placement — snaps every cell to a legal position: aligned to the row grid, no overlaps with other cells or macros.
What can go wrong
Routing congestion

If a small region of the die has too many signals passing through it, the router cannot fit all the wires there. The placer produces a congestion heat map — dark areas need to be resolved by reducing cell density (larger die or lower utilization) or restructuring the logic to reduce interconnect between modules.

Macro placement blocks cell rows

Large SRAM macros placed in the wrong position can cut off standard cell rows or create regions the router cannot reach. Macro placement usually requires manual iteration — try different corner/edge positions and check congestion.

Stage 6 — Clock Tree Synthesis

Stage 6 Clock Tree Synthesis (CTS) tool: OpenROAD

The clock signal must arrive at every flip-flop at nearly the same time. If it arrives at flip-flop A 500 ps before flip-flop B, and A feeds B, then A's output must travel the full path from A to B in one clock period minus that 500 ps. The skew directly eats into timing budget.

CTS builds a clock tree — a balanced binary tree of buffers that distributes the clock from its single source to every leaf flip-flop, matching the propagation delay to each leaf as closely as possible.

Key metrics after CTS:

  • Clock skew — the difference in arrival time between the earliest and latest leaf. Target under 100 ps for a 50 MHz design (the clock period is 20 ns; 100 ps is 0.5% of that).
  • Insertion delay — the total time from clock source to leaves, added by the buffer tree. Typical: 1–3 ns. This shows up as a constant offset in timing reports but does not affect slack.

sky130 CTS uses dedicated clock buffer cells (sky130_fd_sc_hd__clkbuf_*) that are characterized specifically for clock distribution — better drive strength and lower skew than general buffers.

Stage 7 — Routing

Stage 7 Routing tool: OpenROAD (TritonRoute)

The router connects every cell port to every other port it is supposed to be connected to, using the available metal layers (met1–met5 in sky130). It works in two phases:

  1. Global routing — divides the die into a coarse grid and assigns each net to routing channels, identifying which regions of the die each wire passes through.
  2. Detailed routing — assigns exact wire tracks and via positions within each channel, following the global routes while satisfying all design rules.

Vias connect wires on different metal layers. Each via takes area and adds resistance. The router minimizes via count alongside wire length.

Design rules are the foundry's geometric constraints: minimum wire width, minimum spacing between adjacent wires on the same layer, minimum via size, minimum metal enclosure around a via. sky130 has hundreds of these rules. The router must satisfy all of them — DRC (Stage 8) verifies this afterwards.

What can go wrong
Failed routes (unrouted nets)

If the router cannot fit all wires, some nets are left unrouted. This is a hard failure — the design is not complete. Fix by reducing cell density (larger die), reducing the number of signals crossing congested regions, or adjusting macro placement to open routing channels.

Long wires with high resistance

Long wires on thin metal layers have significant resistance, which adds delay and may cause timing failures in STA. The router can insert repeater buffers along long routes to restore signal strength. OpenROAD does this automatically for critical nets.

Stage 8 — Sign-off Checks

Before a GDS file can be submitted, three checks must pass completely. No exceptions. A single DRC violation or a negative timing slack is a hard failure — the foundry will reject the submission.

STA Static Timing Analysis tool: OpenSTA

STA re-runs on the fully routed design, using extracted wire delays — real resistance and capacitance values measured from the layout geometry — instead of the estimated delays used during synthesis and placement. This is the final authoritative check.

Two types of slack must both be non-negative:

  • Setup slack — how much time the slowest path has before the next clock edge captures the result. A flip-flop's input must be stable for a short window before the clock edge (the setup time). If the logic is too slow, the input is still changing when the edge arrives — the flip-flop captures a wrong or metastable value.
  • Hold slack — the flip-flop's input must also remain stable for a short window after the clock edge (the hold time). If a fast path propagates new data to the input before hold time has elapsed on the receiving flip-flop, the old data is corrupted. Hold violations are typically fixed by inserting small delay buffers on the fast path.

STA is run at multiple PVT corners — combinations of process variation (fast, typical, or slow transistors from manufacturing variation), supply voltage (nominal ±10%), and temperature (−40°C to +125°C). The worst setup slack comes from the slow-voltage-hot corner; the worst hold slack comes from the fast-voltage-cold corner. Both must pass.

DRC Design Rule Check tool: Magic

DRC checks every polygon in the layout against the foundry's geometric manufacturing rules. sky130 has hundreds of rules. Common violations:

  • Metal spacing violation — two wires on the same layer are closer than the minimum allowed gap. The foundry cannot reliably manufacture them without risking a short.
  • Minimum width violation — a wire is narrower than the minimum that can be reliably etched. It would break or have excessive resistance.
  • Via enclosure violation — the metal surrounding a via does not extend far enough past the via boundary. The via would not make reliable contact.

Zero DRC violations are required. Every violation must be fixed before submission. In OpenLane, DRC is run automatically with Magic after routing.

LVS Layout vs Schematic tool: Netgen

LVS extracts the circuit from the physical layout — reading every transistor and every wire drawn — and compares it against the gate-level netlist to verify they are electrically identical.

  • Every transistor in the layout must match a transistor in the netlist.
  • Every wire connection in the layout must match a wire in the netlist.
  • No extra connections, no missing connections, no unintended shorts.

A passing LVS means that what was physically drawn is electrically the same as what was synthesized. A failing LVS means the layout was modified in a way that diverged from the netlist — either a routing short, a missing connection, or a manual edit that was not reflected in the netlist.

Stage 9 — GDS Export

Stage 9 GDS Export tool: Magic

Once STA, DRC, and LVS all pass, the layout is exported as a GDSII file (.gds). GDSII is the universal interchange format for integrated circuit layout — every foundry in the world accepts it. The file encodes every polygon on every layer of the design as a binary stream of geometric shapes.

For sky130, the GDS includes the pre-built cell layouts of every standard cell instantiated in the design (merged from the PDK's own GDS files), every I/O pad, and every SRAM macro. The result is the complete, self-contained physical description of the chip.

The GDS is accompanied by a .lef (abstract layout for integration into larger designs) and a .lib (timing model), though for a standalone chip submission only the GDS is strictly required.

Stage 10 — Tapeout Submission

Stage 10 Submission — Efabless / Google MPW platform: efabless.com

For sky130, tapeout happens through the Efabless Chipignite or Google MPW programs. Multiple independent designs are combined onto one wafer — each team gets a small die area and shares the fabrication cost.

  1. Submit the GDS plus supporting files (.lef, .lib, and a caravel wrapper — a standardized harness that Efabless requires for the shared power and I/O infrastructure) to the Efabless platform.
  2. Efabless runs their own DRC and LVS on the submission. Their checks must also pass.
  3. Multiple teams' designs are tiled onto a single MPW wafer (Multi-Project Wafer). The cost of one wafer run is split across all submissions.
  4. SkyWater fabricates the wafers. Typical turnaround from submission close to chips in hand: 3–6 months.
  5. Efabless dices the wafers, packages the individual dies, and ships them to each submitter.

Cost: free for the MPW slot (Google-sponsored). Each submitter receives a small number of packaged chips — typically 5–10, depending on die size.
