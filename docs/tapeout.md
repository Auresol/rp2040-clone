# RTL to Tapeout

This document explains the process of taking the RTL in this repository and turning it
into a real silicon chip. It covers every stage in order, what each stage produces, what
tools are used, and what can go wrong.

The target process for this project is **SkyWater sky130** — a 130 nm open-source process
developed by SkyWater Technology and Google. 130 nm means the smallest feature that can be
reliably drawn on the chip is 130 nanometres wide. It is not a bleeding-edge node, but it
is open, well-documented, and accessible for free through the Efabless/Google MPW program.

---

## Overview

```
RTL (SystemVerilog)
    │
    ▼
sv2v — convert SystemVerilog to plain Verilog
    │
    ▼
Synthesis (Yosys) — map RTL to sky130 standard cells
    │  output: gate-level netlist (.v)
    ▼
Floorplanning (OpenROAD) — set die size, place I/O pads, define power grid
    │  output: placed floorplan (.def)
    ▼
Placement (OpenROAD) — position every standard cell inside the die
    │  output: placed netlist (.def)
    ▼
Clock Tree Synthesis (OpenROAD) — build balanced clock distribution
    │  output: placed + clocked netlist
    ▼
Routing (OpenROAD) — connect cells with metal wires across layers
    │  output: routed layout (.def)
    ▼
Sign-off checks
    ├── STA  — static timing analysis, every path meets the clock period
    ├── DRC  — design rule check, all geometries follow foundry rules
    └── LVS  — layout vs schematic, layout matches the netlist
    │
    ▼
GDS export (Magic) — produce GDSII layout file
    │
    ▼
Tapeout submission to foundry
```

The toolchain that automates this entire flow is **OpenLane**. It wraps Yosys, OpenROAD,
Magic, Netgen, and several other tools into a single configurable pipeline driven by a
JSON config file. Running OpenLane from start to finish on a design produces a GDS file
ready for submission.

## Stage 1 — Convert SystemVerilog to Verilog (sv2v)

The RTL in this repo is written in **SystemVerilog** (`.sv` files). SystemVerilog is a
superset of Verilog that adds convenient features: `logic` types, interfaces, `always_ff`,
`always_comb`, packed structs, and more. Vivado (the FPGA tool) handles SystemVerilog
natively.

Most open-source ASIC tools — in particular Yosys — have limited or incomplete
SystemVerilog support. The first step is to convert everything to plain Verilog using
**sv2v**, a tool that mechanically lowers SystemVerilog constructs to equivalent Verilog.

```bash
sv2v rtl/soc/*.sv rtl/soc/**/*.sv -w separated
```

Things that can go wrong here:

- **Unpacked array ports** — SystemVerilog allows port declarations like
  `input logic [7:0] data [3:0]` (an array of four 8-bit values). Plain Verilog does not
  support unpacked arrays on ports. These must be flattened to `input logic [31:0] data`
  before sv2v runs.
- **`automatic` in always blocks** — SystemVerilog tasks inside `always` blocks can be
  declared `automatic` (meaning local variables are re-created on each call). Verilog does
  not support this in synthesizable code. Remove `automatic` or restructure the logic.
- **$readmemh with FPGA-specific init** — The SRAM init via `$readmemh` is for FPGA only.
  For ASIC, memory is a separate macro (see Stage 2) and `$readmemh` must be removed from
  the synthesizable RTL.

## Stage 2 — Replace FPGA Primitives with ASIC Equivalents

The FPGA version of this design uses features that do not exist in a standard cell library:

### BRAM → OpenRAM SRAM macro

On FPGA, the 64 KB SRAM is built from `RAMB36` primitives — dedicated memory blocks
hard-wired into the FPGA. In an ASIC there are no RAMB36 blocks. Instead, memory is
provided as **hard macros** generated by a tool called **OpenRAM** using the sky130
standard cell library.

An OpenRAM-generated SRAM macro is a pre-characterized block: its timing, power, and
area are known precisely. It plugs into the design as a black box with a standard
read/write port interface.

Steps:
1. Determine the required SRAM configuration: width (32 bits), depth (16384 words = 64 KB),
   number of ports (2 — one for instruction fetch, one for data), read/write latency.
2. Run OpenRAM with the sky130 PDK to generate the macro.
3. Replace the `sram_bank.sv` BRAM inference logic with an instantiation of the generated
   macro.
4. Provide the macro's `.lib` (timing) and `.lef` (layout dimensions) files to OpenLane
   so the placer and router know its size and pin locations.

### LUTRAM → standard cell registers or small SRAM macros

The PIO FIFOs use LUTRAM (distributed RAM in FPGA fabric). In ASIC this does not exist.
Options:
- For small FIFOs (≤ 64 bits deep): replace with plain registers synthesized from
  flip-flops. This is area-inefficient but correct.
- For larger FIFOs: generate a small SRAM macro from OpenRAM and instantiate it.

## Stage 3 — Synthesis (Yosys)

**Yosys** reads the Verilog netlist and maps it to the **sky130 standard cell library** —
a collection of hundreds of pre-characterized logic gates, flip-flops, and buffers
that SkyWater has physically designed and verified in 130 nm silicon.

Synthesis does three things in sequence:

1. **Elaboration** — parse the RTL and build an internal representation of the logic.
2. **Optimization** — simplify logic, remove dead code, merge redundant gates.
3. **Technology mapping** — replace the abstract logic with actual cells from the sky130
   library (e.g., `sky130_fd_sc_hd__and2_1` for a 2-input AND gate,
   `sky130_fd_sc_hd__dfxtp_1` for a positive-edge-triggered flip-flop).

The output is a **gate-level netlist** — a Verilog file that contains only cell
instantiations and wire connections, no behavioral logic.

Important synthesis settings for sky130:

- **Standard cell library variant**: sky130 has several drive-strength variants
  (`hd` = high-density, `hs` = high-speed, `ms` = medium-speed, `ls` = low-speed).
  OpenLane defaults to `hd`. Higher drive strength means lower delay but larger area.
- **Target clock period**: tell Yosys the intended clock frequency so it can optimize
  timing-critical paths. Start conservative (e.g. 50 MHz = 20 ns period) for a first
  pass.
- **Flattening**: Yosys can flatten all hierarchy into a single module. Sometimes needed
  for timing optimization across module boundaries. OpenLane controls this.

What can go wrong:

- **Unmapped cells** — if sv2v missed something or there is a construct Yosys does not
  understand, synthesis fails with an unmapped cell. Fix the RTL and re-run.
- **Combinatorial loops** — logic that feeds back into itself with no register in the
  path. Yosys will error. These must be broken with a registered stage.
- **Latches inferred unintentionally** — incomplete `if/else` or `case` statements in
  combinatorial blocks cause Yosys to infer latches. Latches are problematic for ASIC
  timing analysis. All cases must be explicitly covered, or a default assignment must be
  added at the top of the block.

## Stage 4 — Floorplanning

The floorplan defines the physical space the chip will occupy.

**Die size**: determined by the total area of all standard cells plus routing overhead.
OpenLane estimates this from the synthesized netlist. A utilization of 40–60% is typical
— leaving room for routing channels. At 60% utilization, if the cells occupy 1 mm², the
die is ~1.67 mm².

**I/O pad placement**: signals that connect to the outside world (clock, reset, GPIO pins)
need I/O pads around the perimeter of the die. sky130 provides I/O pad cells from the
`sky130_fd_io` library. Each pad is larger than a standard cell — roughly 60 µm wide.
The number of pads is constrained by the perimeter of the die.

**Power planning**: the power grid is defined in the floorplan step.
- A **power ring** runs around the perimeter of the die, connected to the VDD and GND
  supply pads.
- **Power straps** (wide metal wires) run vertically and horizontally across the die,
  branching off the ring and supplying power to every row of standard cells.
- Standard cells connect to VDD/GND through the power rails in their rows.

sky130 has 5 metal layers available for routing:
- **met1** — local connections, power rails in cell rows
- **met2, met3** — signal routing
- **met4, met5** — power straps, clock trunk

What can go wrong:

- **Die too small for the I/O pads**: if the requested die size has a perimeter shorter
  than the total width of all required I/O pads, the floorplan fails. Solution: increase
  the die size, reduce the number of I/O signals, or use differential pairs to share pads.
- **Power IR drop**: if the power straps are too narrow or too sparse, regions of the die
  see a lower effective supply voltage due to resistance in the metal. This slows down
  logic and can cause timing failures. IR drop is checked in sign-off (Stage 7).

## Stage 5 — Placement

The placer positions every standard cell from the netlist inside the die boundary,
within the rows defined by the floorplan. The objective is to minimize total wire length —
cells that are connected to each other should be physically close, to keep routing short.

OpenROAD's placer runs in two phases:
1. **Global placement** — roughly positions cells to minimize estimated wire length,
   ignoring exact row alignment.
2. **Detailed placement** — snaps cells to legal positions (aligned to the cell row grid,
   no overlaps).

Hard macros (the SRAM blocks from Stage 2) are placed **before** standard cells, usually
in the floorplan step. The placer treats them as fixed obstacles and routes standard cells
around them.

What can go wrong:

- **Placement congestion**: if too many nets need to cross a small region of the die, the
  router will not be able to fit all the wires. The placer produces a congestion map —
  high-congestion areas may require reducing utilization or restructuring the logic that
  generates the congested signals.
- **Macro placement conflicts**: large SRAM macros placed in awkward positions can block
  standard cell rows and create dead zones. Macro placement usually requires manual
  tuning.

## Stage 6 — Clock Tree Synthesis (CTS)

The clock signal must reach every flip-flop in the design at nearly the same time.
If the clock arrives at flip-flop A 500 ps before it arrives at flip-flop B, and A drives
B, then A's output must travel from A to B within one clock period minus that 500 ps of
skew. Large skew wastes timing budget.

CTS builds a **clock tree** — a balanced binary tree of buffers that distributes the clock
from its source to every leaf flip-flop, matching the path delay to each leaf as closely
as possible.

Key metrics after CTS:
- **Clock skew** — difference in arrival time between the earliest and latest leaf.
  Target: < 100 ps for a 50 MHz design (the period is 20 ns, so 100 ps is 0.5%).
- **Insertion delay** — time from the clock source to the leaves. This is the overhead
  added by the buffer tree. Typical: 1–3 ns.

sky130 CTS uses specific buffer cells (`sky130_fd_sc_hd__clkbuf_*`) that are
characterized for clock distribution — lower skew and better drive strength than general
buffers.

## Stage 7 — Routing

The router connects all the cells with metal wires, using the available metal layers
(met1–met5 in sky130). It works in two phases:

1. **Global routing** — divides the die into a coarse grid and assigns each net to
   routing channels. Identifies which regions of the die each net passes through.
2. **Detailed routing** — assigns exact tracks and vias within each channel, following
   the global route.

Vias connect wires on different metal layers. Each via adds resistance and takes area.
Minimizing via count is one of the router's objectives alongside wire length.

**Design rules** — the foundry specifies exact geometric rules for what can be drawn:
minimum wire width, minimum spacing between wires on the same layer, minimum via size,
minimum enclosure of a via by its surrounding metal. The router must follow all of these.
After routing, DRC verifies this (see Stage 8).

What can go wrong:

- **Routing congestion / failed routes**: if the router cannot fit all wires, some nets
  are left unrouted. This is a hard failure. Resolution: reduce cell density (larger die),
  restructure the netlist to reduce wire count, or adjust floorplan.
- **Long wires with high resistance**: long wires on thin metal layers degrade signal
  timing. The router may need to insert repeater buffers along long routes.

## Stage 8 — Sign-off Checks

Before a GDS file can be submitted to the foundry, three checks must pass completely.
No exceptions.

### STA — Static Timing Analysis

STA re-runs on the routed design using exact wire delays (extracted from the physical
layout) instead of the estimated delays used during synthesis and placement. This is the
final authoritative check that every path in the design meets the clock period.

Key outputs:
- **Setup slack**: how much time margin the slowest path has before the next clock edge.
  Must be ≥ 0 at all process/voltage/temperature corners.
- **Hold slack**: how much time margin ensures a flip-flop's output doesn't arrive too
  *early* at the next flip-flop (before the receiving flip-flop has had time to capture
  the previous value). Must also be ≥ 0. Hold violations are often fixed by inserting
  delay buffers on the violating path.

STA is run at multiple **PVT corners** — combinations of process variation (fast/typical/
slow transistors), voltage (nominal ± 10%), and temperature (−40°C to +125°C). The
slowest corner determines setup slack; the fastest corner determines hold slack.

### DRC — Design Rule Check

DRC checks every polygon in the layout against the foundry's geometric rules. sky130 has
hundreds of rules. Common violations:

- **Metal spacing violation** — two wires on the same layer are closer than the minimum
  allowed spacing.
- **Minimum width violation** — a wire is narrower than the minimum manufacturable width.
- **Via enclosure violation** — the metal surrounding a via does not extend far enough
  beyond the via boundary.

Zero DRC violations are required for tapeout. DRC is run with **Magic** (open source)
or Calibre (commercial). Magic is used in the OpenLane flow.

### LVS — Layout vs Schematic

LVS compares the physical layout against the netlist to verify they match:
- Every transistor in the layout must correspond to a transistor in the netlist.
- Every connection in the layout must correspond to a wire in the netlist.
- No extra connections, no missing connections, no shorts between nets.

LVS is run with **Netgen** in the OpenLane flow. A passing LVS means the physical design
is electrically identical to what was synthesized.

---

## Stage 9 — GDS Export

Once all sign-off checks pass, the layout is exported as a **GDSII** file (`.gds`).
GDSII is the universal interchange format for integrated circuit layout — every foundry
accepts it. The file contains every polygon on every layer of the design, encoded as a
binary stream of geometric shapes.

For sky130, the GDS also includes the pre-built layout of every standard cell
instantiated in the design (merged from the PDK cell GDS files) and the I/O pad cells.
The final GDS is the complete layout of the chip.

---

## Stage 10 — Tapeout Submission

For sky130, tapeout happens through the **Efabless Chipignite / Google MPW** program:

1. Submit the GDS file plus supporting files (`.lef`, `.lib`, caravel wrapper) to the
   Efabless platform.
2. Efabless runs their own DRC and LVS checks on the submission.
3. Multiple designs are combined onto a single **MPW wafer** (Multi-Project Wafer) —
   many teams share a wafer to split the cost of a fabrication run.
4. SkyWater fabricates the wafers. Turnaround: typically 3–6 months.
5. Efabless dices the wafers, packages the dies, and ships them to submitters.

Cost: free for the MPW slot. You get a small number of packaged chips.

## What This Design Still Needs Before Tapeout

In rough priority order:

1. **Arbiter fix** — the dual-core arbiter bug must be resolved before the design is
   complete. See `docs/HANDOFF.html` Known Issues.

2. **sv2v clean pass** — the RTL needs to be run through sv2v and all conversion errors
   fixed. Known issues: unpacked array ports, automatic in always blocks.

3. **SRAM macro integration** — replace `sram_bank.sv` BRAM inference with an OpenRAM-
   generated sky130 SRAM macro. The macro needs to be generated for the correct size
   (32-bit wide, 16384 deep, dual-port) and integrated into the build flow.

4. **PIO FIFO memory replacement** — the LUTRAM-backed FIFOs in `pio_fifo.sv` need to
   be replaced with either register arrays (for shallow FIFOs) or small SRAM macros.

5. **PIO clkdiv width** — restore the clock divider to 16 bits (current FPGA version
   uses 8 bits to avoid wide counter inference in Vivado — not a concern for ASIC).

6. **I/O pad planning** — count required I/O signals, choose a die size whose perimeter
   fits all pads, and integrate sky130 I/O pad cells.

7. **OpenLane config** — write a `config.json` for the design specifying die size, target
   clock period, macro positions, power strap geometry, and synthesis/routing parameters.

8. **Full OpenLane run + sign-off** — iterate on floorplan, placement, and routing until
   STA, DRC, and LVS all pass clean.
